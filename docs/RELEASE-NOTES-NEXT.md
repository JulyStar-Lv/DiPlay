# DiPlay next release notes

Changes through DiPlay 0.2.19 are documented in [0.2.19 release notes](RELEASE-NOTES-0.2.19.md). Measured checks are in [VALIDATION.md](VALIDATION.md). Device acceptance and remaining failure families are tracked in [connection reliability validation](CONNECTION_RELIABILITY.md).

## Connection setup and recovery

- Wired CarPlay can switch the iPhone to CarPlay mode on head units whose kernel binds its USB audio driver to the iPhone, such as the 8227L in [#518](https://github.com/shihabal3amri/DiPlay/issues/518). DiPlay detached the driver by claiming each interface, but Android's `releaseInterface()` asks the kernel to attach the driver again, so it was back before the switch (`usbfs: interface 0 claimed by snd-usb-audio while … sets config #6`). DiPlay now keeps those claims, then closes and reopens its connection to the iPhone, which drops the claims without reattaching the driver, and switches after that. The report still logs `USB configuration select target=6 ok=… detached=…`. Pending in-car acceptance.
- **Automatically turn on the car hotspot** can start it on head units whose firmware offers no hotspot command over ADB. Android refuses DiPlay's own request there: `No field mService` on an Android 10 head unit and `NoSuchMethodException … startTethering` on an Android 12 DiLink 5.0 Song L, both in [#616](https://github.com/shihabal3amri/DiPlay/issues/616). With network ADB approved, DiPlay now asks the shell to start Wi‑Fi tethering with the car's saved hotspot, which Android allows: through the connectivity service on Android 7.0–10 and the tethering service on Android 11 and newer. The report logs `car hotspot: shell tethering request …`. Pending in-car acceptance.
- **Settings → Connection** now has the authentication choice (**Local offline** or **USB/CH341**), so a driver who removed the CH341 adapter can switch back to Local without connecting first. That choice was only in the menu inside CarPlay, which cannot be reached when CarPlay cannot connect ([#696](https://github.com/shihabal3amri/DiPlay/issues/696)). CarPlay reads the choice again each time it starts.
- Wired CarPlay comes back within seconds after **Save and reconnect**. DiPlay ended its session and started a new one at once, and the iPhone, still in CarPlay mode from the old session, accepted iAP2 and StartSession but opened no CarPlay connection until it reset USB 30–150 s later ([#335](https://github.com/shihabal3amri/DiPlay/issues/335)). When the iPhone is still in the mode of a session DiPlay started on the same USB connection, DiPlay now asks for CarPlay mode again first, as a fresh connection does. The report shows `previousSessionOnThisEnumeration=true action=request-transition`. Pending in-car acceptance.

## Display

- **CarPlay map on dashboard (experimental)** finds the cluster on BYD firmware that names it `fission_magicsentry` (controller 13) or `sission_magicsentry` (controller 17), at the same 1920×720 size as DiLink 4's `fission_bg_xdjaVirtualSurface`. A controller-13 car listed it as a presentation display, but DiPlay looked only for the DiLink 4 name, so nothing appeared on the cluster. A build that accepted the name drew the map there ([#552](https://github.com/shihabal3amri/DiPlay/issues/552)). Pending in-car acceptance on the release build.
- On DiLink 3, the settings card for the dashboard map no longer offers the two DiLink 4 cluster routes (**DiLink 4 cluster video via ADB** and **Platform 21 cluster task**). Either one stops DiLink 3 from creating its dashboard display, so the map stayed off, and only the ADB route showed a warning ([#722](https://github.com/shihabal3amri/DiPlay/issues/722)). When either is on, the card and the setup guide show the warning with a button that turns both off.
- **CarPlay map on dashboard (experimental)** uses the same full-map and side-map layers on the Leopard 5 Ultra (system 34.1.23) as on the measured DiLink 5.1 firmware. It drew into a layer this cluster never shows ([#301](https://github.com/shihabal3amri/DiPlay/issues/301)). Pending in-car acceptance.
- With **Efficient video** (HEVC) on, a head unit without a hardware HEVC decoder now gets H.264. Android had picked its own software decoder instead: a Spreadtrum SC7731E head unit (Android 8.1) decoded every session in software with `OMX.google.hevc.decoder` while DiPlay logged `decoder=hardware`, and music skipped ([#727](https://github.com/shihabal3amri/DiPlay/issues/727)). The report says `HEVC is on, but no hardware decoder plays it`. **HEVC software decoder** still keeps HEVC on Android 10 and later.

## Audio, calls and Siri

- An app voice message can use the head unit's microphone. DiPlay opened the microphone only after the iPhone's first audio packet, and an app that records a voice message (Douyin on a Leapmotor T03, [#566](https://github.com/shihabal3amri/DiPlay/issues/566)) asks for the microphone without playing anything, so recording never started. When no audio arrives within 0.5 s, DiPlay now opens the microphone anyway. Calls still wait for the call audio. The report logs `Audio: microphone started without downlink audio`. Pending in-car acceptance.
- When the head unit's microphone returns no audio for 1 s, DiPlay restarts recording up to three times, and no longer reads the empty microphone in a tight loop. On the same Leapmotor T03 (Android 7.1), some recordings started with no input device and returned nothing for the whole Siri request or call ([#566](https://github.com/shihabal3amri/DiPlay/issues/566)). The report logs `Microphone: recording restarted … reason=no-audio routedDeviceType=…`. Pending in-car acceptance.
- **Settings → Audio → Calls on the loudspeaker** is for an Android phone or tablet used as the head unit. It plays CarPlay calls on the device's loudspeaker and uses its hands-free microphone. Android plays calls on such a device's earpiece and records them with the handset microphone, so the driver heard calls only close to the screen and had to speak into it (Xiaomi MIX 2S, Android 10, [#701](https://github.com/shihabal3amri/DiPlay/issues/701)). It is off by default and applies from the next call. The report adds `loudspeaker=true|false` to `Audio: mode entered communication`. Pending acceptance.

## Diagnostics

- When DiPlay crashes, the next diagnostic report shows where: a new **Last crash recorded by DiPlay** section lists the exception, its causes and the code it was thrown from, redacted like the rest of the report. Android 11+ only recorded `reason=java_crash`, so a crash when the DiYou launcher card opens DiPlay could not be traced ([#463](https://github.com/shihabal3amri/DiPlay/issues/463)). The record stays on the head unit until a report is saved and shared.
- The phone page's server (**Get the report on a phone**, settings backup) wakes from waiting for a browser every 0.25 s instead of only after its 10-minute idle timeout, so closing it never waits on a pending accept. On the macOS JVM used for the unit tests, closing it while it waited hung the test run.
- On a head unit where BYD's HUD gateway package exists but refuses DiPlay's binding, DiPlay no longer retries it every 300 ms. On a Bliss OS tablet that was about 200 refused binds a minute, each logged by DiPlay and by Android ([#609](https://github.com/shihabal3amri/DiPlay/issues/609)). Retries now back off from 0.3 s to one minute, and the refusal is logged once.
